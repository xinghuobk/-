## 2. 需求分析与技术栈的核心结论

### 2.1 核心设计理念（一句话）

**ParaJudge** = **四阶段结构化辩论**（证据构建 → **Moderator 主持下** Coach+Speakers 辩论 → 检察官-辩护律师审理 → 五维专业法官裁决） × **目标驱动 Agent 异质性** × **证据闭包约束** × **辩论质量守门**（去重/主题漂移/超时） × **创新保护机制** × **类判决书推理链输出**

### 2.2 技术栈核心选型（一张表）

| 维度 | 选型 | 理由 |
|:---|:---|:---|
| **工作流编排** | **LangGraph 0.2.22** | StateGraph 完美契合四阶段流程；parallel node 支持五法官并行；Checkpointer 免费获得状态持久化 |
| **用户接口** | FastAPI 0.111 + Typer 0.12 + Jinja2 3.1 | FastAPI 自动文档/类型安全；Typer 与 FastAPI 同团队；Jinja2 零学习成本渲染裁决书 |
| **数据模型** | **Pydantic v2 2.9.2** | 全栈唯一数据模型；与 FastAPI/Typer 原生集成；JSON 序列化自动完成 |
| **LLM Provider** | **`openai` 1.43 SDK** + **`dashscope` 1.20** + **自研 Mock Provider** | 统一抽象 → 新增 Provider 仅需实现 `LLMProvider.chat()` 一个函数；Mock 保证零 API Key 也能端到端运行 |
| **配置管理** | **pydantic-settings 2.5** + **PyYAML 6.0** + **python-dotenv 1.0** | 支持 .env 环境变量 + 结构化 DebateConfig + YAML 领域知识库，三套配置全栈打通 |
| **可靠性** | **tenacity 9.0**（指数退避重试） + **httpx 0.27**（现代异步 HTTP 客户端） | 每次外部调用都有 ≥3 次自动重试；失败自动降级到 Mock Provider |
| **学术检索** | **arxiv 2.1** + **Semantic Scholar API** + **Crossref API** | 三源检索覆盖大多数论文；JSON 结果 → EvidenceBrief Pydantic 模型 |
| **成本/监控** | **tiktoken 0.7**（OpenAI 官方分词器） + JSON 结构化日志 | 每次 LLM 调用精确记录 input/output token，可配置预算告警自动邮件通知 |

## 5. ★ Moderator 主持人角色详细开发计划

> **说明**：Moderator 是 Phase 1 辩论引擎的核心控制节点，不产出论点，但负责整个辩论的节奏、质量与秩序。它直接消费现有的 schemas.py（7 个 Moderator 模型已完成），并调用 Coach/Speaker 产出内容。本章节给出 Moderator 的详细开发分解。

### 5.1 Moderator 在系统中的位置（一句话）

```
  [证据构建 Phase 0] → [Moderator 主持下的辩论 Phase 1] → [审理 Phase 2.1] → [裁决 Phase 2.2]
                                 ↑
                          持有 5 阶段状态机
                          分配发言权给 Coach/Speaker
                          做质量守门（去重/漂移/超时）
                          产出 DebateSummary → 作为 Phase 2.1 的输入
```

### 5.2 Moderator 的输入/输出（IO 契约）

| 方向 | 数据结构 | 来源/去向 | 备注 |
|:---|:---|:---|:---|
| 输入（配置） | `DebateConfig` + `ModeratorConfig` | `cli.py` / `api.py` 传给 orchestration | `moderator_config` 可由 CLI/API 直接覆盖 |
| 输入（证据） | `EvidenceBrief` | Phase 0 产出 | 论点引用必须在其中 |
| 输入（Agent） | `List[Coach]` + `List[Speaker]` | Phase 1 内部实例化 | 正反双方各 1 Coach + 2–3 Speakers |
| 输出（结构化） | `DebateSummary` | → Phase 2.1 审理 | 核心产物 |
| 输出（索引） | `ArgumentIndex` | → Phase 2.1 审理 | 所有论点的结构化索引 |
| 输出（日志） | `List[ModeratorWarning]` | 嵌入 `DebateSummary.warnings` | 可审计 |

### 5.3 Moderator 内部实现分解（按依赖顺序）

```

│  src/debate/moderator.py                                            │
├──────────────────────────────────────────────────────────────────────┤

│    class Moderator:                                                  │

│      - _state: {"current_phase": DebatePhase,                       │
│                  "turn_count": int, "phase_start_time": float, ...} │
│      - _argument_index: ArgumentIndex                               │

│                                                                      │
│  5.3.2 五阶段状态机驱动主循环（≈80 行）                               │
│    run() -> DebateSummary                                            │
│      ↳ OPENING_STATEMENTS（立论）                                    │
│        for each side: 按 Coach 分配的 opening_max_rounds 轮发言      │
│      ↳ CROSS_EXAMINATION（交叉质询）                                 │
│        正反交替提问，允许 POI（FR-313）                              │

│      ↳ CLOSING_STATEMENTS（总结陈词）                                │
│        closing_max_rounds 轮，禁止 POI                              │
│      ↳ DONE（完成）                                                  │
│        产出 DebateSummary，统计 phase_durations / total_duration    │
│                                                                      │
│  5.3.3 发言分配与 TurnRequest 生成（≈40 行）                         │
│    _request_next_speaker(side, phase, round_idx) -> TurnRequest    │
│      ↳ 计算 timebox_max_tokens / timebox_max_seconds               │
│      ↳ 为每个 Speaker 生成唯一 turn_id                              │
│                                                                      │
│  5.3.4 质量守门（≈80 行）★ 核心复杂模块                              │
│    _quality_gate(argument) -> Tuple[bool, Optional[Warning]]        │
│      ↳ 5.3.4.1 duplicate检测：embedding相似度 vs ArgumentIndex     │
│        · 默认阈值 duplicate_threshold = 0.85                        │
│        · 在 strict 模式：>0.85 直接拒绝；normal：警告；loose：忽略   │
│      ↳ 5.3.4.2 主题漂移检测：关键词覆盖 / BM25 相似度              │
│        · 对比 argument 与 problem + EvidenceBrief 关键词           │
│        · 默认 off_topic_threshold = 0.4                            │
│      ↳ 5.3.4.3 token 截断：tiktoken / len(word.split) 估算        │
│        · 超过 max_tokens_per_turn 时截断最后 n 句                 │
│      ↳ 5.3.4.4 引用合法性验证：检查 evidence_refs 都在 Brief 中   │
│        · INVALID_CITE 警告                                          │
│                                                                      │
│  5.3.5 时间片管理（≈40 行）                                           │
│    _monitor_timebudget(phase_start_time, phase) -> bool            │
│      ↳ 超时检测：time.monotonic() - phase_start_time                │
│      ↳ 超过 max_total_seconds 时立即强制进入 DONE                   │
```

### 7.2 T1–T4 开发分解（按模块/文件/方法三级）

#### 7.2.1 T1: AEBG 论点-证据二部图（Argument-Evidence Bipartite Graph）

```
新建文件：src/debate/aebg.py（≈150 行）

  class ArgumentEvidenceBipartite:
    ├─ __init__(evidence_brief, embeddings_provider)
    │   - 构建图 G，添加证据节点
    │   - 每个证据节点携带 confidence / relevance 属性
    │
    ├─ add_argument(argument) → Dict[str, float]   ★ 核心方法
    │   - 添加论点节点
    │   - 添加边：论点 ↔ 引用的证据
    │   - 计算并返回 4 项评分（见下表）
    │
    ├─ _evidence_support(arg_node) → float
    │   - 度数 / 最大度数
    │
    ├─ _evidence_diversity(arg_node, emb_matrix) → float
    │   - 1 − 邻居间平均余弦相似度
    │
    ├─ _pagerank(arg_node) → float
    │   - Personalized PageRank，以高置信度证据为源
    │   - 依赖 networkx.pagerank()
    │
    └─ _closure_reach(arg_node) → float
        - 是否存在高置信度证据邻居（布尔软化到 [0,1]）

  QualityGate 升级：
    _quality_gate(argument) 在原 duplicate 检测基础上，新增：
      if aebg.combined_score < 0.30 → REJECT（低质量论点）
      if aebg.combined_score in [0.30, 0.55] → ACCEPT+WARNING
      if aebg.combined_score > 0.55 → ACCEPT
```

**评分表（T1 中实现的 4 项指标）**：

| 指标 | 计算方式 | 取值范围 | 高分含义 |
|:---|:---|:---|:---|
| evidence_support | degree(a)/max_degree | [0,1] | 论点引用了大量不同证据 |
| evidence_diversity | 1 − mean(cos_sim(邻居证据)) | [0,1] | 引用的证据在语义上多样 |
| pagerank | 以高置信度证据为源的 PPR | [0,1] | 论点靠近「权威」证据源 |
| closure_reach | 高置信度证据邻居占比 | [0,1] | 论点有可靠证据支撑 |
| **combined_score** | 上述 4 项加权平均（等权或 BO 优化） | [0,1] | **综合质量评分** |

**新增依赖**：`networkx`（纯 Python，轻量图库，已在技术栈汇总文档 §5 中评估）

**测试**：`tests/debate/test_aebg.py`（≈60 行）——构造一张 3 证据 + 5 论点的小图，验证每个评分的范围和排序关系。

#### 7.2.2 T2: DPP 多样性约束（Determinantal Point Process）

```
新建文件：src/debate/dpp_sampler.py（≈100 行）

  class DPPArgumentSampler:
    ├─ __init__(lambda_diversity=1.0, num_candidates=3)
    │
    ├─ sample(candidates, quality_scores, emb_matrix) → int
    │   ★ 核心方法：返回选中候选的 index
    │   - 构建 L 矩阵：L_ij = q_i·q_j·exp(−λ·cos_dist(i,j))
    │   - 选择使 det(L_SS) 最大的单元素（等价于 argmax q_i·(1−min_sim_to_history)）
    │   - 简化版：不做完整 DPP greedy，直接用「质量×与历史的不相似度」
    │
    └─ _rejection_sample(candidates, quality_scores, emb_matrix,
                          history_embs, theta=0.70) → int
        └─ 快速降级方案：生成 K 个候选，选第一个与历史
           论点 embedding 余弦相似度 < theta 的

  AgentBase 升级：
    _generate_argument() 改为 _generate_candidates() → 生成 K 个草案
    然后由 DPP sampler 选 1 个作为正式论点
```

**超参数**：
- `λ`（DPP 多样性强度）= 1.0（默认），消融范围 0.5–4.0
- `K`（候选数量）= 3（每轮让 LLM 多生成 2 个额外候选，成本增加 ≈60% 但质量提升）
- `θ`（拒绝采样阈值）= 0.70，与历史论点相似度低于此阈值才通过

**测试**：`tests/debate/test_dpp.py`（≈40 行）——构造一组高重复候选，验证 DPP 选择的论点与历史相似度显著低于随机选择。

#### 7.2.3 T3: KS 检验收敛检测（Kolmogorov-Smirnov Test）

```
新建文件：src/debate/stability.py（≈60 行）

  class DebateStabilityDetector:
    ├─ __init__(alpha=0.05, min_rounds=3, max_rounds=8)
    │
    ├─ record(judge_scores_5d_vector)   ★ 每轮辩论后调用
    │   - 记录当前轮的 5 位法官评分
    │
    └─ should_stop() → Tuple[bool, Optional[float]]
        ★ 核心方法：返回 (是否停止, 本轮 p-value)
        - 如果历史 < min_rounds → False
        - 否则做两样本 KS 检验：ks_2samp(S_t, S_{t-1})
        - 如果 p-value > α → True（收敛）
        - 如果已达 max_rounds → True（硬上限）
        - 否则 → False

  Moderator 升级：
    在自由辩论阶段，每轮结束调用 stability.record(judge_light_score)
    然后检查 stability.should_stop()，若为 True → 提前进入总结陈词
```

**新增依赖**：`scipy.stats.ks_2samp`（`scipy` 是标准科学计算库，与 `numpy` 一起使用）

**关键设计点**：
- 「轻量级打分」不要求法官写完整判决书，只输出 0–100 的整数分 + 1 句理由（约 100 tokens / 法官）
- **无超参数可调**——α=0.05 是统计学标准，max_rounds=8 是工程上限
- 可以额外做一个「方差趋势」辅助信号——如果 std(S_t) < 0.05·std(S_0)，也视为收敛（即使 KS p-value 略低于 0.05）

**测试**：`tests/debate/test_stability.py`（≈40 行）——构造两组人工评分序列：一组快速收敛，一组持续波动，验证检测器行为正确。

#### 7.2.4 T4: DS 证据理论融合（Dempster-Shafer Fusion）

```
新建文件：src/judgment/ds_fusion.py（≈120 行）

  class DSEvidenceFusion:
    ├─ __init__(n_levels=10)
    │   - 离散化 0–100 分为 n_levels 个档位
    │
    ├─ fuse(judge_scores, judge_confidences, weights=None)
    │   → Dict[str, Any]
    │   ★ 核心方法：
    │   - 每位法官 → 高斯型 BPA（基本概率指派）
    │   - 用 Dempster 合成规则顺序合并 5 个 BPA
    │   - 返回 {final_score, uncertainty, confidence_interval, full_bpa}
    │
    ├─ _gaussian_bpa(score, sigma, weight) → np.ndarray (n_levels+1,)
    │   - 为单个法官构建 BPA
    │   - 最后一维是 m(Θ) = 1−weight（无知度）
    │
    └─ _dempster_combine(bpa1, bpa2) → np.ndarray
        └─ 标准 Dempster 合成（归一化冲突质量）

  FinalJudge 升级：
    原 weighted_score() 改为 ds_fuse()
    返回的 JudgmentReport 新增字段：
      .uncertainty_score      # m(Θ)，取值 [0,1]
      .confidence_interval    # [lo, hi]，如 [45, 78]
      .needs_human_review     # 当 uncertainty > 0.40 时为 True
```

**参数**：
- `n_levels = 10`（离散化为 10 档，每档 10 分，足够精细又不过分稀疏）
- `judge_confidences`：默认全部 = 15 分（每位法官对自己评分的 ±1σ 不确定性）
- `uncertainty_threshold = 0.40`（超过此阈值标记为「建议人工复核」）

**测试**：`tests/judgment/test_ds_fusion.py`（≈50 行）——验证 3 个手动构造的测试用例：
1. 5 法官一致 → 低 uncertainty
2. 5 法官严重分歧 → 高 uncertainty
3. 1 个法官离群（90分 vs 其他 40 分）→ uncertainty 升高但低于完全分歧

### 7.6 风险与降级方案

| 风险 | 概率 | 影响 | 降级方案 |
|:---|:---|:---|:---|
| `networkx` PageRank 在大图上变慢 | 低（每轮 <100 节点） | 中（延迟 >100ms） | 改用纯 Python 简化版：`pagerank_iter(G, personalization, max_iter=20)` 手写实现（≈20 行）；或预计算只每 3 轮刷新一次 |
| `scipy` 太重（~40MB），部署不便 | 中 | 低（仅 T3 需要 ks_2samp） | 降级：用纯 Python 实现 KS 检验的近似版本（Wald–Wolfowitz 游程检验，或简单地检查两轮评分差 < 5% 即视为收敛） |
| DPP 候选 K=3 导致 token 成本翻倍 | 中 | 中（每轮论点生成的 token 从 1× 变 3×） | 默认启用 K=1（即不启用 DPP），仅在「高质量模式」CLI 参数下启用 K=3；或实现「动态 K」——问题简单时 K=1，问题复杂时 K=3 |
| DS 融合的冲突质量 > 0.95 导致不稳定 | 中（极端分歧时） | 低（仅影响不确定性输出） | 冲突 > 0.95 时自动降级为简单加权平均，并在 warnings 中记录「DS 融合冲突过高，已降级」 |
