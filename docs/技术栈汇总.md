## 1. 一句话概述

**ParaJudge** = **Python 3.10+** + **FastAPI** + **Typer CLI** + **LangGraph 编排** + **多 LLM Provider**（OpenAI 兼容 / DashScope / Mock） + **Pydantic v2 数据模型** + **Jinja2 裁决书** + **学术检索 (arXiv/Semantic Scholar/Crossref)** + **YAML 领域知识库** + **JSON 持久化**。

## 3. 核心技术选型一览

> 以下按 **分层** 组织，表格式为：**技术 / 版本 / 为什么选择它 / 与其他方案的对比**。**Moderator（主持人）** 作为辩论阶段的"控制中枢"，对编排框架（LangGraph）、数据模型（Pydantic）、异步调度（asyncio）均有特殊要求，已在相关条目中以 **【Moderator 关联】** 标注。

### 3.1 编程语言

| 技术 | 版本 | 为什么选择它 | 与其他方案的对比 |
|:---|:---|:---|:---|
| **Python** | 3.10 / 3.11 / 3.12 | 1) LangChain/LangGraph 官方原生语言，API 映射最自然 2) 数据科学/LLM 生态最完整（pydantic、httpx、tiktoken、sentence-transformers 等）3) 团队成员熟悉度高，招聘池大 4) 3.10+ 的 `match/case` 与 `async` 对 Moderator 状态机实现非常友好 | ✅ **vs Go**：Go 性能高，但 LLM/Agent 生态落后，LangGraph 无官方 Go SDK；**vs Rust**：开发速度慢，PyO3 绑定成本高；**vs TypeScript**：LangGraph.js 存在但生态与文档成熟度弱于 Python |

### 3.2 用户接口层（CLI / API / 渲染）

| 技术 | 版本 | 为什么选择它 | 与其他方案的对比 |
|:---|:---|:---|:---|
| **FastAPI** | 0.111.1 | 1) Pydantic v2 原生集成，类型安全自动文档 2) **ASGI 原生**，适配 Moderator 的异步多阶段辩论（每阶段可独立挂起）3) 性能接近 Node.js，开发速度优于 Django REST Framework | ✅ **vs Django REST Framework**：重、同步第一、启动慢；**vs Flask**：无原生异步、类型支持弱；**vs aiohttp**：需要手写文档与模型校验 |
| **uvicorn[standard]** | 0.30.6 | 1) FastAPI 官方推荐 ASGI 服务器 2) `standard` 版带 HTTP/2、WebSocket、静态文件支持 3) 支持 `--reload` 开发调试 | ✅ **vs hypercorn**：同样成熟但不如 uvicorn 普及；**vs daphne**：主要服务于 Django 通道 |
| **Typer** | 0.12.5 | 1) FastAPI 同一团队出品，类型提示自动生成 argparse 2) 与 `rich` 搭配可输出 Moderator 辩论的彩色状态（"ROUND 1 / CROSS_EXAMINATION / 剩余 45s"）3) 支持 `--moderator-strictness` 等自定义子选项 | ✅ **vs click**：Typer 基于 click 但接口更现代；**vs argparse**：手写代码量翻倍 |
| **rich** | 13.7.1 | 1) 终端彩色表格，用于实时打印 Moderator 时间片/质量守门状态 2) 进度条、树形结构，调试状态机直观 | ✅ **vs colorama**：仅颜色；**vs termcolor**：功能弱得多 |
| **Jinja2** | 3.1.4 | 1) 裁决书 HTML/Markdown 双格式渲染的成熟方案 2) Moderator 产出的 `DebateSummary` 可直接传入模板生成结构化裁决报告 3) 零学习成本 | ✅ **vs Mako**：功能更强但 API 不友好；**vs 手写 f-string**：不可维护，模板不可复用 |

### 3.3 编排框架（LangGraph 及生态）

| 技术 | 版本 | 为什么选择它 | 与其他方案的对比 |
|:---|:---|:---|:---|
| **LangGraph** | 0.2.22 | **【Moderator 关联】** 1) `StateGraph` 天然匹配 Moderator 的 5 阶段状态机：`OPENING_STATEMENTS → CROSS_EXAMINATION → FREE_DEBATE → CLOSING_STATEMENTS → DONE` 2) `parallel node` 支持 Phase 2.2 五位 Judge 并行评估 3) `Checkpointer` 让大型辩论可中断/恢复，Moderator 的 `DebateSummary` 可持久化 4) `asyncio` 原生异步，便于 Moderator 实现时间片超时控制 | ✅ **vs AutoGen**：对话模式成熟但结构化流程控制弱；**vs CrewAI**：Role/Goal 模式直观，对多阶段辩论不够灵活；**vs 自研 asyncio 状态机**：工作量 ≥ 3 人月且无 Checkpointer/可视化；**vs Prefect/Airflow**：DAG 设计，不擅长 Agent 对话交互 |
| **langchain-core** | 0.3.15 | 1) LangGraph 依赖，提供 `Runnable` 抽象 2) `BaseMessage`、`HumanMessage` 等消息基类，供 Moderator 封装 TurnRequest 3) 与 Pydantic 紧密集成 | ✅ **vs 纯手写接口**：失去生态，需要自己实现 Prompt 模板/消息体系/回调 |
| **langchain** | 0.3.10 | 1) Agent 模板与工具函数（JSON parser、output parser）复用 2) Moderator 的质量守门可复用 LangChain 的 OutputParser 做结构化检查 | ✅ **vs 仅安装 langchain-core**：可减小依赖体积，但需手写部分 output parser |

### 3.4 数据模型（Pydantic / 配置 / YAML）

| 技术 | 版本 | 为什么选择它 | 与其他方案的对比 |
|:---|:---|:---|:---|
| **Pydantic v2** | 2.9.2 | **【Moderator 关联】** 1) Moderator 新增模型：`ModeratorConfig`（严格度/阶段配置）、`TimeboxConfig`（每阶段时间片）、`TurnRequest`（当前轮到哪位 Coach 发言）、`ModeratorWarning`（质量守门告警）、`DebateSummary`（阶段总结与统计）均由 Pydantic 定义 2) 与 FastAPI OpenAPI 自动文档无缝 3) v2 基于 Rust，性能 5~10 倍于 v1 | ✅ **vs dataclass + marshmallow**：双重代码、无 FastAPI 自动文档；**vs attrs**：与 FastAPI 集成弱；**vs msgspec**：更快但生态与 FastAPI 集成弱于 Pydantic |
| **pydantic-settings** | 2.5.2 | 1) `.env` + YAML 双重加载，类型安全 2) Moderator 的默认严格度、各阶段轮次可通过 `ModeratorConfig` 从环境变量覆盖 | ✅ **vs python-dotenv 手写 dict**：无类型校验；**vs dynaconf**：功能多但较重 |
| **PyYAML** | 6.0.2 | 1) DomainKB 领域知识库 YAML 文件加载 2) 可读的纯文本格式，便于版本化管理（Git diff 友好）3) Moderator 的规则配置也可放在 YAML 中 | ✅ **vs JSON**：不适合人工编辑；**vs TOML**：不适合多层嵌套结构；**vs SQLite**：对"领域知识库"这种少量条目数据过度复杂 |

### 3.5 LLM Provider

| 技术 | 版本 | 为什么选择它 | 与其他方案的对比 |
|:---|:---|:---|:---|
| **openai** SDK | 1.43.0 | 1) Chat Completions 模式稳定，支持 JSON mode，便于 Moderator 对输出做结构化校验 2) 兼容任意 OpenAI 兼容端点（vLLM、Ollama、LM Studio 等）3) GPT-4o-mini 性价比高，适合 Moderator 的轻量决策（判断发言质量、是否越界） | ✅ **vs LangChain-only**：SDK 直接使用更轻量；**vs litellm**：可作为统一抽象层，但新增一层依赖 |
| **dashscope** | 1.20+ | 1) 通义千问官方 SDK，中文质量优秀 2) 作为 OpenAI 的中文备用 Provider，缓解 OpenAI 价格/可用性风险 3) Moderator 对中文裁决场景可优先使用 qwen 系列 | ✅ **vs Anthropic Claude (bedrock)**：中文支持弱、国内访问延迟高；**vs 自研 HTTP 封装**：维护成本高 |
| **Mock Provider（自定义）** | — | 1) **不依赖外网**，保障 CI 可离线运行 2) seed 固定 → 可复现，适合 Moderator 状态机的单元测试 3) 零成本 | ✅ **vs 真实 LLM**：速度快 100x，但需额外开发 mock 逻辑 |
| **tiktoken** | 0.7.0 | 1) OpenAI 官方分词器，精确 token 计数 2) Moderator 可据此判断发言是否超限（token 预算）3) 成本估算 | ✅ **vs 粗估字符数**：误差可到 ±30%；**vs sentencepiece**：需加载模型文件 |

### 3.6 网络 / 重试 / HTTP

| 技术 | 版本 | 为什么选择它 | 与其他方案的对比 |
|:---|:---|:---|:---|
| **httpx** | 0.27.2 | 1) 现代化 HTTP 客户端，同步/异步双模式 2) `AsyncClient` 可与 Moderator 的 `asyncio` 事件循环共享 3) 支持 HTTP/2、连接池、超时控制，适合外部 API 调用 | ✅ **vs requests**：无原生 async；**vs aiohttp**：API 不如 httpx 直观 |
| **tenacity** | 9.0.0 | 1) LLM/外部 API 的指数退避重试 2) Moderator 对 Speaker 发言失败时可重试（带上限），避免整轮崩溃 3) 可配置回调、最大重试、退避策略 | ✅ **vs 手写重试循环**：易出错、无统一策略；**vs backoff**：功能相近但 tenacity 更流行 |
| **requests** | 2.32.3 | 1) CLI/脚本中的简单同步请求（如检索 arXiv 的简化脚本）2) 行业标准 | ✅ **vs 全部 httpx 化**：可做但没必要；保持 requests 作为同步场景备用 |

### 3.7 检索与解析（学术 / PDF）

| 技术 | 版本 | 为什么选择它 | 与其他方案的对比 |
|:---|:---|:---|:---|
| **arxiv** | 2.1.3 | 1) 主流学术元数据源，覆盖 CS/physics 等领域最全面 2) Moderator 的证据闭包校验主要依赖 arXiv ID | ✅ **vs 直接 HTTP 调用 arXiv API**：需手写解析；已封装好 |

### 3.8 测试 / 质量

| 技术 | 版本 | 为什么选择它 | 与其他方案的对比 |
|:---|:---|:---|:---|

### 3.9 可选 / 实验性增强

## 7. LangGraph 替代方案评估

> 为支撑"选择 LangGraph"这一关键决策，列出几种可替代方案的优劣势，便于团队讨论与决策回滚。

| 方案 | 优点 | 缺点 | 适用场景 | 对 ParaJudge 的适配难度 |
|:---|:---|:---|:---|:---|
| **LangGraph（最终选择）** | 1. StateGraph 原生状态管理 2. parallel node 并行评估 3. Checkpointer 4. LangChain 生态 5. 可视化调试工具 | 1. 学习曲线 2. 版本仍 0.x | **本项目标准选择** | ✅ 1 周内上手 |
| **AutoGen** | 1. 多 Agent 对话模式成熟 2. 社区活跃 | 1. 对结构化流程控制不够精细 2. 微软重写（v0.4 架构变动大） | 开放式 Agent 对话、工具调用型任务 | ⚠️ 中等：需重写裁决的并行节点 |
| **CrewAI** | 1. Role/Goal/Tool 模式直观 2. 文档友好 | 1. 对辩论-裁决这种多阶段复杂流程不够灵活 2. 对状态持久化弱 | 顺序型任务流水线 | ⚠️ 中等：并行法官需自定义 |
| **自研 asyncio 状态机** | 1. 完全可控 2. 零外部依赖 3. 轻量 | 1. 重新实现状态管理 2. 无可视化 3. 维护成本高 4. 无并行节点框架 | 极简项目 / 极端性能约束 | ⚠️ 高：工作量 ≥ 3 人月 |
| **Prefect / Airflow** | 1. 成熟的任务编排 2. 可视化/监控 | 1. 设计为批处理/DAG，不擅长 Agent 对话式交互 2. 重量级 | 数据流水线 | ❌ 不合适 |
| **Dramatiq / Celery** | 1. 任务队列 2. 异步执行 | 1. 仅解决执行调度，无状态图概念 | 异步任务分发 | ❌ 仅做底层执行器 |

**结论**: LangGraph 在"控制精细度 + 并行能力 + Checkpointer + LangChain 生态"的组合上显著优于其他方案，是当前最佳选择。其他方案中，**AutoGen** 可作为特定 Agent（如开放探索型）的辅助框架，但不替代 LangGraph 的编排地位。

### 7.1 Moderator 5 阶段状态机与 LangGraph StateGraph 的契合度

Moderator 的核心是一个 **5 阶段状态机**，其设计与 LangGraph 的 `StateGraph` 在以下维度天然匹配：

| 维度 | Moderator 5 阶段状态机 | LangGraph StateGraph 的对应支持 |
|:---|:---|:---|
| **状态定义** | 全局状态中需记录：`current_phase`（当前阶段）、`round_index`（第几轮）、`turn_of_coach`（轮到哪位 Coach）、`remaining_seconds`（剩余时间片）、`debate_summary`（累积总结）、`moderator_warnings`（质量守门告警列表） | `TypedDict` / Pydantic `BaseModel` 均可作为 State；LangGraph 自动处理 reducer 式状态更新 |
| **阶段节点** | `OPENING_STATEMENTS → CROSS_EXAMINATION → FREE_DEBATE → CLOSING_STATEMENTS → DONE` | 每个阶段 = 一个 `node`；`add_node("opening_statements", moderator_node)` 直接映射 |
| **条件边** | 进入下一阶段的条件："本轮已完成"、"CROSS_EXAMINATION 轮次已达上限"、"时间片用尽"、"质量合格" | `add_conditional_edges(from_node, condition_fn, mapping)` 完美表达 Moderator 的"根据回合数/时间/质量决定是否进入下一阶段" |
| **并行节点** | FREE_DEBATE 阶段可同时让正反 Coach 各自独立搜索证据/构造论点 | `add_node("pro_free", pro_free_fn)` + `add_node("con_free", con_free_fn)` + 条件边收敛到 Moderator；LangGraph 天然支持并发调度 |
| **中断 / 恢复** | 大型辩论可中途挂起，稍后继续；Checkpointer 持久化 `DebateSummary` 与各阶段状态 | `MemorySaver` / `SQLiteSaver` 原生支持 `thread_id` 级别断点；Moderator 无需自己写持久化 |
| **异步 / 时间片** | Moderator 的时间片需要准确"到点即跳"（比如 CROSS_EXAMINATION 每轮 ≤ 60s） | LangGraph 全链路由 `async` 实现；可在外层用 `asyncio.wait_for(coro, timeout=...)` 包裹每个节点调用，配合 `tenacity` 做重试 |
| **可视化 / 调试** | Moderator 的阶段流转需要可追溯（便于团队 review 辩论质量） | LangGraph Studio 可直接渲染图结构；`get_state_history(thread_id)` 可回放任意阶段的完整状态 |

> **结论**：Moderator 的 5 阶段状态机 = LangGraph StateGraph 的一个 **典型用例**。节点是阶段，条件边是阶段推进规则，全局 State 是 Moderator 的运行时状态与 `DebateSummary`。如果改用自研 asyncio 状态机，Moderator 需要自行实现：状态 reducer、持久化、并发调度、可视化工具——这部分工作量预计可被 LangGraph **减少 70% 以上**。

# 2. 生成 .env（使用默认即可，无需 API Key）
cp .env.example .env

# 3. Mock Provider 端到端测试（基础模式）
parajudge run "AI 开源是否会让研发公司失去竞争优势？" --provider mock --max-rounds 2

# 3b. ★ Moderator 模式示例（完整 5 阶段状态机 + 质量守门 + 时间片）
#     --moderator-strictness strict : 质量守门严格（任何违规即中止当前发言）
#     --opening-rounds 1            : OPENING_STATEMENTS 阶段正反各发言 1 轮
#     --cross-exam-rounds 2         : CROSS_EXAMINATION 阶段进行 2 轮交叉质询
#     --closing-rounds 1            : CLOSING_STATEMENTS 阶段各做 1 轮总结
#     --max-total-seconds 120       : 整个辩论的墙钟时间上限 120 秒
parajudge run "大模型是否应当被要求开源核心推理权重？" \
  --provider mock \
  --moderator-strictness strict \
  --opening-rounds 1 \
  --cross-exam-rounds 2 \
  --closing-rounds 1 \
  --max-total-seconds 120

# 4. API 模式
uvicorn api:app --host 0.0.0.0 --port 8000
curl -X POST http://localhost:8000/api/v1/parajudge/run \
  -H "Content-Type: application/json" \
  -d '{"problem": "是否应该让大模型在医疗诊断中直接给出建议？", "provider": "mock", "moderator": {"strictness": "strict", "opening_rounds": 1, "cross_exam_rounds": 2, "closing_rounds": 1, "max_total_seconds": 120}}'

## 10. 关键风险与替代

| 风险项 | 概率 | 影响 | 缓解方案 / 替代 |
|:---|:---|:---|:---|
| **LangGraph 0.x API 变动** | 中 | 中 | 1) 严格锁定 `langgraph==0.2.22` 版本 2) 封装 `src/orchestration` 层，隔离 LangGraph API 变动 3) 关注官方 changelog |
| **OpenAI API 价格 / 可用性** | 中 | 高 | 1) 支持 DashScope 作为主力中文模型 2) Mock Provider 保障开发 3) token 预算与费用告警 |
| **arXiv 检索质量波动** | 低 | 中 | 多源检索（Semantic Scholar + Crossref）交叉验证；冷领域允许低 evidence_coverage |
| **LLM 响应格式不稳定** | 中 | 中 | 1) 用 Pydantic 模型 + JSON mode 2) 格式重试 3) 失败降级为结构化文本解析 |
| **Python 版本差异** | 低 | 低 | CI 测试 3.10 / 3.12 / 3.14；避免使用 3.12+ 专属语法 |
| **大依赖（langchain-community）** | 中 | 低 | 按需安装；或只安装 langchain-core + 手写适配；可做 `--no-deps` 精简化安装 |
| **PDF 解析依赖重（pymupdf）** | 低 | 低 | PDF 解析为 P2 需求；若遇安装问题可临时禁用，不影响核心辩论流程 |
| **向量库资源占用（chromadb）** | 低 | 低 | P3 实验性；可推迟启用；或改用纯 BM25 + sqlite-utils 替代 |
| **中文 Prompt 质量差异** | 中 | 中 | 1) 中英文双模板 2) 以 qwen 系列为中文基线测试 3) 中文裁决书渲染测试 |
| **多 Agent 可复现性** | 中 | 高 | 1) Mock Provider 保证 seed 固定 2) 真实 LLM 设置 `temperature=0.0` 做确定性推理测试 3) 测试集人工评估容忍 ±5% 偏差 |
| **★ R-M1：Moderator 时间片精度问题** | **中** | **中** | **风险描述**：若 Moderator 的时间片计时基于 `time.monotonic()` 做轮询检查，当事件循环被长时 I/O（LLM 调用、arXiv 检索）阻塞时，计时可能漂移 ±5–15 秒，导致"超时未打断"或"过早打断"。**缓解方案**：1) 使用 `asyncio.wait_for(coro, timeout=timebox)` 包裹每个发言节点调用，由事件循环原生机制在超时点抛 `TimeoutError`；2) Moderator 的总时间上限用 `asyncio.timeout(overall_seconds)` 做外层守卫；3) 对 `TimeoutError` 统一处理为"发言截断"并记录到 `ModeratorWarning`；4) CI 中加入"时间片精度"专项测试（mock 长时任务，验证误差 ≤ 1 秒）。**替代方案**：纯进程级超时（`multiprocessing.Process` + `join(timeout)`）可规避 GIL 阻塞，但会破坏 LangGraph 的共享状态 |
| **★ R-M2：Moderator 质量守门的误判率** | **中** | **高** | **风险描述**：质量守门依赖：(a) 结构化字段校验（Pydantic）(b) 证据引用校验（arXiv ID 存在性）(c) 发言去重（embedding 相似度 ≥ 阈值）(d) 论点新颖性（与历史发言的语义夹角）。其中 (c)(d) 的相似度阈值对问题类型敏感（抽象伦理问题 vs 事实性科学问题），固定阈值可能导致：漏判（让重复发言通过）或过严（误杀有效新论点）。**缓解方案**：1) 对质量守门的四类检查分别设置 `ModeratorConfig` 可调阈值（`similarity_threshold` / `evidence_required_ratio` / `max_warnings_per_speech`）；2) P0 阶段收集 50–100 条真实/模拟辩论样本，标注"误判 vs 正确"，用统计学习做自适应阈值（按 ProblemClassifier 识别的问题类型映射不同默认阈值）；3) 每次质量守门检查都写入 `ModeratorWarning` 列表（含 `confidence` 字段），并在 `DebateSummary` 末尾附"质量守门审计摘要"，便于人工 review；4) strict/lenient/permissive 三档，默认使用 lenient，避免误判造成整轮崩溃；5) CI 内置"守门回归测试"集，固定阈值不能变动。**替代方案**：先用纯规则（Pydantic + arXiv ID）实现 (a)(b)，(c)(d) 推迟到 P1/P2，由人工先 review 一段时间再自动开启 |
